# Технический аудит Bodkin и Canary

Срез исходников: 9 сентября 2026. Проверка документов завершена 10 сентября 2026. Назначение: выбор исходной базы для собственного торгового помощника Pons V2 / Robinhood Chain.

## Решение

Использовать модули Bodkin для обнаружения запусков, обогащения данных, объяснимого скоринга и торговых маршрутов. Из Canary взять модель снимков и детерминированные правила изменений. Создать единое управление позициями, приказами, бюджетами и журналом. Не запускать два независимых движка вокруг одного кошелька.

Оба репозитория содержат работающий код, собираются и проходят имеющиеся тесты. Однако заимствование торгового движка без исправлений неприемлемо: обнаружены дефекты контроля налогов, разделения режимов и конкурентного исполнения. Это инженерный аудит выбранных критических путей, а не полная сертификация безопасности контрактов или mainnet-исполнения.

Оба проекта в коде указывают chainId 4663 и один Pons V2 factory `0x7eD598BcEf8bd9Edd8C97A195C6d13f40801EC7e`, совпадают основные hook/StateView/PoolManager адреса. Это подтверждает совместимость предметной модели, но не актуальность каждого адреса или ABI в сети. Веб-документация Pons имеет разные версии: нельзя переносить V1/V3 адреса в этот V2/V4 адаптер. Здесь сравнивались исходники; актуальные deployment-параметры остаются обязательным интеграционным gate.

## Найденные проблемы

### A1. Ошибка чтения налога разрешает вход — высокая важность, воспроизведено

`waitForTax()` ловит RPC-ошибку и присваивает tax=0, затем возвращает ok=true. `readCurveState()` также заменяет неудавшееся чтение currentSnipeTaxBps на 0. Подставной RPC, всегда бросающий исключение, дал `{ok:true,taxBps:0}`. Фактическая транзакция может отклониться из-за minOut, но заявленная налоговая защита уже обходится; нельзя рассчитывать на revert как на проверку правила.

Исправление: unknown запрещает вход, bounded retry, свежая котировка для фактического получателя, отказ при недоступной налоговой информации.

Источники: [snipe.ts:110–118](https://github.com/Phosphenq/bodkin/blob/27b801ad5358061fc10f151cc1e305974df89178/src/snipe.ts#L110-L118), [curve.ts](https://github.com/Phosphenq/bodkin/blob/27b801ad5358061fc10f151cc1e305974df89178/src/pons/curve.ts).

### A2. Paper/live позиции смешиваются — высокая важность, статический путь

`positions.json` общий; `openPositions()` фильтрует только status. Движок продаёт через `sellAnywhere(...,!live)`, используя режим процесса, а не pos.dryRun. Запуск live после paper способен попытаться продать токены paper-позиции из реального кошелька, если баланс позволяет. Обратный запуск может пометить live-позицию закрытой без реальной продажи. Файл также не отделяет chain и wallet.

Исправление: mode/chain/wallet обязательны в ключах состояния и проверках каждой команды; paper executor не имеет signer.

Источники: [positions.ts:28–55](https://github.com/Phosphenq/bodkin/blob/27b801ad5358061fc10f151cc1e305974df89178/src/trade/positions.ts#L28-L55), [snipe.ts:207–238](https://github.com/Phosphenq/bodkin/blob/27b801ad5358061fc10f151cc1e305974df89178/src/snipe.ts#L207-L238). Реальная продажа для демонстрации не выполнялась.

### A3. Автоматические выходы могут пересекаться — высокая важность, статический путь

`manage()` запускается setInterval каждые 5 секунд без блокировки предыдущего прохода. `closing` заполняется при ручном close, но автоматический sellOut не добавляет туда позицию. Долгое ожидание receipt допускает второй автоматический или ручной выход по той же позиции.

Исправление: одна очередь исполнения на wallet, атомарный переход позиции в closing, idempotency key, контроль pending/unknown транзакций. Тестировать зависший receipt и конкуренцию manual/auto.

Источник: [snipe.ts:207–251](https://github.com/Phosphenq/bodkin/blob/27b801ad5358061fc10f151cc1e305974df89178/src/snipe.ts#L207-L251).

### A4. Бюджет не резервируется для ожидающих покупок — высокая важность, статический путь

`spent` увеличивается после завершения buy. Несколько onLaunch могут пройти decide на одном spent, дождаться налога параллельно и суммарно превысить budget. busy ограничивает число позиций, но не зарезервированные ETH. После рестарта spent=0: это соответствует названию session budget, но не является устойчивым лимитом пользователя.

Исправление: резервировать максимальную сумму до отправки; атомарно проверять spent+reserved+new; после receipt списывать фактическую сумму и снимать резерв. Явно определить период бюджета и восстановление при рестарте.

Источник: [snipe.ts:151–196](https://github.com/Phosphenq/bodkin/blob/27b801ad5358061fc10f151cc1e305974df89178/src/snipe.ts#L151-L196).

### A5. Ошибка RPC выглядит как исчезновение резерва — высокая важность, воспроизведено

Canary snapshot заменяет неудавшийся realQuoteReserve на 0n и возвращает успешный снимок. Воспроизведение: предыдущий резерв 1000, следующее чтение падает → liquidityWei=0 → curve-reserve-drop. FallbackReader при этом второй RPC не вызывает. Аналогичная подстановка нулей есть для fee reads. Нельзя напрямую соединять level=leave с продажей.

Исправление: поле с quality и error, сравнение только валидных наблюдений, fallback при неполном критическом снимке, отсутствие критических данных — отдельное событие degraded.

Источники: [rpc.ts:372–389](https://github.com/Gipppp121/canary/blob/376714b5a3134218020cf0f0e664ce5fa895578d/src/chain/rpc.ts#L372-L389), [fallback-reader.ts](https://github.com/Gipppp121/canary/blob/376714b5a3134218020cf0f0e664ce5fa895578d/src/chain/fallback-reader.ts).

### A6. JSON-состояние недостаточно для исполнения и журнала

В обоих проектах синхронная перезапись файла, без транзакционного журнала. Повреждённый файл приводит к пустому состоянию. Bodkin записывает позицию после завершения buy; авария между сетевым исполнением и записью оставит покупку без позиции. Canary сохраняет последнюю версию снимка, не хронологию событий.

Исправление: SQLite с транзакциями; intent до отправки, tx hash сразу после отправки, reconciliation после рестарта, явная ошибка повреждения, резервные копии. Отдельный импорт JSON не нужен первому чистому релизу.

Источники: Bodkin `trade/positions.ts`, `snipe.ts`; Canary `watch/store.ts`.

### A7. PnL и ручные операции требуют единого учёта

Вход записывается как запрошенный ethPerBuy, хотя quoteBuy умеет clamp/refund. Gas не входит в entryEth и формулу PnL. Продажа в pool считает выход через разницу ETH-баланса: посторонний перевод в интервале может исказить результат. CLI sell работает от баланса и не обновляет position ledger. Автоматический движок закрывает всю позицию; массив exits сам по себе не реализует частичные TP.

Исправление: fill receipts, actual spent/refund, fee/gas ledger, остаточная себестоимость, все ручные/автоматические действия через один order service. Для pool выбрать и проверить способ извлечения fills из конкретных контрактных событий/trace; баланс использовать для reconciliation, не как единственную атрибуцию.

Источники: `trade/curveTrade.ts`, `trade/poolTrade.ts`, `cli-trade.ts:144–157`, `snipe.ts:194–196`.

### A8. Локальная board не готова к открытому размещению

Bodkin слушает 127.0.0.1, но POST start/close/rules не имеют application auth, проверки Origin или CSRF token. Loopback ограничивает прямое сетевое подключение, но не заменяет проверку вызывающей стороны. Canary имеет control token для proxy/non-loopback, но прямому localhost доверяет. Эксплуатация через браузер не проверялась.

Исправление: локальная сессия с token, Host/Origin allowlist, запрет неавторизованных control-запросов, read-only публичный API. Не публиковать торговый control plane через простой reverse proxy.

Источники: [Bodkin server.ts:106–139](https://github.com/Phosphenq/bodkin/blob/27b801ad5358061fc10f151cc1e305974df89178/src/board/server.ts#L106-L139), Canary `ui/control-auth.ts`.

### A9. Полнота наблюдения и восстановление

Canary проверяет последние 250 launch candidates плюс pinned tokens по умолчанию, а не все ERC-20 кошелька. Ошибка balanceOf пропускает токен. Последняя сделка ищется в ограниченном окне; если её там нет, timestamp unknown и сигнал отсутствия объёма не сработает. Снимки читаются несколькими запросами без общего blockNumber. Bodkin при включении polling начинает у текущей головы; durable cursor и гарантированного backfill после outage в этом пути нет.

Исправление: собственные открытые позиции автоматически pin; общий блок снимка; quality/age на экране; durable cursor с overlap/dedup и обработкой reorg. После долгого outage исторические сигналы показываются, но устаревшие входы автоматически не исполняются.

Источники: Canary `chain/rpc.ts:157–160,277–349,353–468`; Bodkin `pons/launches.ts`.

### A10. Уведомления и документация

Telegram best effort, ошибка отправки проглатывается, дедупликация живёт в RAM и отмечается до подтверждения доставки. Это допускает потерю или повтор после рестарта. В Canary `docs/LIMITATIONS.md` остался текст v0.2 об отсутствии pool indexing, хотя в v0.4 код уже есть. Для нашего продукта состояние функций должно описываться по коду и проверкам.

## Оценка разработки

Оценка для одного опытного TypeScript/EVM разработчика, рабочий день ~6 продуктивных часов. Это экспертная оценка по найденным изменениям, не измеренная скорость команды.

| Пакет | Рабочие дни |
|---|---:|
| Перенос адаптеров, notices, согласование зависимостей и deployment checks | 2–3 |
| SQLite, orders/positions, разделение режимов, бюджет, восстановление | 4–6 |
| Feed, quality snapshots, правила Canary, pin и backfill | 3–5 |
| Paper fills, расходы, TP/SL/trailing/partial, журнал | 3–5 |
| Единый web UI, presets, экспорт, demo, Telegram outbox | 4–6 |
| Интеграционные сценарии, сбои, документация и packaging | 3–5 |
| Итого paper beta | **19–30 дней** |
| Live executor, nonce/receipt recovery, защитные проверки, fork tests | +5–8 |
| Ограниченная live-проверка и исправления по её результатам | +3–5 |
| Полный V1 с live | **27–43 дня** |

Планировать 20–30% резерва: примерно 5–8 недель для paper beta и 7–12 недель для полного V1 при пятидневной неделе. Платный RPC, хостинг и внешний security review в оценку не включены. Протокольные изменения или отсутствие подходящего RPC могут увеличить календарное время. Токен, token gating, многопользовательский SaaS и бренд-дизайн не входят в эту оценку.
