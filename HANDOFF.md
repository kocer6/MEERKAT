# MEERKAT — exact continuation state

Updated 2026-09-10 (M2.2 checkpoint). Read AGENTS.md and PLAN.md. User authorizes incremental GitHub checkpoints; target kocer6/MEERKAT main. Two-day PAPER MVP takes priority over full V1.

## Implemented

Node 24 / TypeScript project with no runtime npm dependencies. Built-in node:sqlite ledger stores account, orders, positions and journal; fills are journal events. State changes are transactional. Amounts serialize as decimal strings. Reservations prevent concurrent budget overspend. Duplicate order keys do not buy twice. Exit locks prevent concurrent closes. Recovery releases interrupted paper reservations and reopens interrupted exits; call recover only at single-process startup.

PaperEngine supports entry filters, quotes, TP/SL/trailing/max hold, manual full close and valuations. Unknown opening tax blocks entry; unknown reserve remains null. Demo is synthetic and offline: 1 ETH -> 0.1 buy -> 0.14 sell -> 1.04 balance, zero synthetic gas. No wallet, signing or real market data.

M1.2: `validateRules`/`assertRules` in src/rules.ts enforce runtime bounds on every field of `Rules` (minScore 0..100 int, maxTaxBps 0..10000 int, maxPositions >=1 int, maxGasWei non-negative bigint, quoteMaxAgeMs >0, takeProfitBps >0 int, stopLossBps 1..9999 int, trailingBps 0..9999 int, maxHoldMs >0). `PaperEngine`'s constructor calls `assertRules(rules)`, so a malformed config throws immediately at construction instead of silently reaching budget or exit-rule logic later.

New this checkpoint (M2.2): `entryReasons` in src/rules.ts now returns granular, independent reasons instead of two combined generic ones, so a rejection is explainable rather than just "rejected". Score is split into `score is unreadable` (non-finite: NaN/Infinity — data could not be read at all), `score exceeds the maximum of 100` (impossible/invalid reading), and `score below minimum threshold` (known-good data that just doesn't qualify). Opening tax is split into `opening tax unknown` (A1 regression fix — wording deliberately unchanged so the existing PaperEngine-level test keeps passing), `opening tax reading is invalid` (non-integer/negative), and `opening tax exceeds limit`. Every applicable reason is returned (not just the first match), so a caller sees the full picture. This distinguishes three outcome classes: matched (empty reasons), rejected (known data fails a threshold), and unreadable (data could not be read — must block entry exactly like a failing filter, never default to a passing value).

Files: src/types.ts, rules.ts, ledger.ts, paper.ts, demo.ts, cli.ts; test/paper.test.ts, test/rules.test.ts, test/smoke.test.ts. Original implementation; upstream code is not imported yet. Add upstream MIT notices when importing.

## Push method note

Git CLI push is unavailable in this sandbox (no credentials, no `.netrc`, no `gh`, no GitHub MCP connector — confirmed again this session). The M1.2 checkpoint was pushed successfully through the GitHub web editor in a connected browser (clipboard-paste into GitHub's CodeMirror editor, commit directly to `main`), using the user's already-authenticated GitHub session — no OAuth grants or credentials were handled directly. That push was independently verified by cloning fresh into a separate directory and confirming `git rev-parse HEAD` matched `git ls-remote origin main`, plus a clean `npm ci && npm test` pass (15/15) in that fresh clone. Repeat the same browser-based push method for future checkpoints. Caution observed during pushes: full-document select+paste in GitHub's CodeMirror editor is unreliable for larger files — `ctrl+a` sometimes only selects the currently-rendered (virtualized) viewport, silently leaving stale content outside it. The reliable sequence is: click into the editor, `ctrl+End`, `ctrl+shift+Home` (select from the true end to the true start), `Delete`, confirm the editor shows the placeholder/empty state, re-write the clipboard, then paste. Also note `document.querySelector('.cm-content').textContent` only reflects the currently-scrolled viewport (virtualized DOM), not the whole document — verify a paste by scrolling to both the very top and very bottom (ctrl+Home / ctrl+End) and screenshotting both, or by re-fetching the raw file from GitHub after commit and diffing against the local source.

## Known limits

Single-user/single-process paper core, not a live or multi-wallet ledger. No schema migration/version gate yet. Rules are supplied in code (runtime-validated at PaperEngine construction, but there is still no config file/env/UI loader that would exercise that path end-to-end — M4 will need one). Entry data (score, openingTaxBps, source) is currently supplied directly by callers/fixtures; there is no live discovery/quote adapter yet, so `entryReasons`'s unreadable-data handling has only been exercised with hand-constructed NaN/null inputs, not a real RPC failure path. Quote callbacks are internal adapters; external API requires its own runtime validation when M3 adapters land. Paper fills do not modify chain liquidity. A1 is fixed at the entryReasons boundary (unknown tax always blocks entry); A5 (reserve RPC failure) is handled at the reserveDrop boundary in rules.ts (returns null, never a false zero) but has no live RPC adapter test yet — A2–A4/A6–A10 from the audit are not yet addressed in product code. No UI, chain adapter, real quote validation, alerts, hosting or gating. MVP is NOT complete.
